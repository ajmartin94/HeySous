<objective>
Fix three wiring gaps where the Mini App settings toggles do not fully control the reminder system, and add integration tests to prevent regression.

Purpose: The settings page gives users the impression they control reminders, but three gaps exist: (1) toggling morning_enabled/prep_alerts_enabled does not regenerate reminders, so already-queued reminders still fire; (2) the poller delivers reminders even when the household is muted; (3) start_cooking reminders are generated regardless of prep_alerts_enabled. This plan closes all three gaps.

Output: Patched settings route, patched poller, integration test file.
</objective>

  <action>
    Fix three gaps identified by code audit:

    **Gap 1: Settings PUT does not regenerate reminders.**
    `createSettingsRoutes` in `src/mini-app/routes/settings.ts` currently only takes `sqlite`. It needs a `regenerateReminders` callback.
    - Change the factory signature to `createSettingsRoutes(sqlite, opts?: { regenerateReminders?: (householdId: string) => void })`.
    - After the successful UPDATE in `updateSettings`, if any of `morning_enabled`, `prep_alerts_enabled`, or `muted_until` was in the update payload, call `regenerateReminders(householdId)`.
    - Update `src/mini-app/router.ts` to pass the callback. The router is created in `src/main.ts` -- thread `regenerateReminders` through. Check how the mini-app router is instantiated in main.ts and pass the callback accordingly.

    **Gap 2: start_cooking reminders not gated by prepAlertsEnabled.**
    In `src/reminders/generator.ts` around line 261, the `start_cooking` block runs unconditionally for each meal. Wrap the entire start_cooking generation block (lines 261-365) in `if (settings.prepAlertsEnabled) { ... }`. This is the correct semantics: "prep alerts" encompasses both advance prep guidance AND start-cooking nudges.

    **Gap 3: Poller does not check muted_until before delivery.**
    In `src/reminders/poller.ts`, the `tick()` function calls `getDueReminders()` which returns all pending reminders across all households. The poller then delivers them without checking if the household is muted.
    Two options (choose the simpler one):
    - Option A: Add a `getSettings(householdId)` call in the poller tick loop and skip if muted. This requires adding `reminderRepository.getSettings` to the poller deps interface.
    - Option B: Modify `getDueReminders()` in repository.ts to JOIN against application_settings and exclude muted households. This is cleaner (single query).
    Choose Option B: Update the `getDueReminders()` SQL in `src/reminders/repository.ts` to:
    ```sql
    SELECT r.* FROM reminders r
    LEFT JOIN application_settings s ON r.household_id = s.household_id
    WHERE r.status = 'pending' AND r.due_at <= ?
      AND (s.muted_until IS NULL OR s.muted_until < ?)
    ORDER BY r.due_at ASC
    ```
    This uses the same `nowUnix()` value for both checks.

    **Write integration tests** in `tests/reminders/settings-integration.test.ts`:
    - Use an in-memory better-sqlite3 database with initializeReminders
    - Test that generateReminders with morningEnabled=false produces no morning_summary rows
    - Test that generateReminders with prepAlertsEnabled=false produces no start_cooking rows
    - Test that getDueReminders excludes muted households
    - Test that getDueReminders includes households where muted_until is in the past
