       - The `unknown` type avoids importing grammY keyboard types into stream-sender (it's just passed through to Telegram API).

    2. In the `finalize` implementation inside `createTelegramStreamSender`, accept the options parameter and pass `reply_markup` to every `editMessageText` call and `sendFormattedMessage` call:
       - For the normal reply path (line ~252): `await ctx.api.editMessageText(chatId, messageId, finalText, { parse_mode: "HTML", reply_markup: options?.reply_markup });`

Check its signature first. If it doesn't support it, for short replies, after sending the fresh message, do a separate edit to add the markup. OR simply skip reply_markup for short replies (edge case, acceptable).
       - For the long reply / split path (line ~239): Skip reply_markup (splitting creates multiple messages, can't attach to all). This is fine.

    3. Also expose a `getMessageId(): number | null` method on the interface so the processor can do a post-finalize edit if needed as a fallback. Add to the interface and return `messageId` from the closure.

    4. In `src/pipeline/processor.ts`, move the deep-link keyboard building (lines ~729-771) to BEFORE the finalize call (lines ~670-688). The flow becomes:
       - Build the keyboard from trackedToolCalls (the existing logic)
       - Call `streamSender.finalize(cleanText, { reply_markup: keyboard })` if keyboard exists, otherwise `streamSender.finalize(cleanText)`
       - Remove the old `ctx.reply("Open in app:", ...)` call entirely

    5. For the non-streaming path (lines ~689-703), keep using a separate message approach since there's no stream sender. But change from `ctx.reply("Open in app:", ...)` to editing the sent message. Since `sendFormattedMessage` returns message objects, check if it returns message IDs. If not, the non-streaming path can keep using `ctx.reply` -- it's a rare fallback.

    6. Comment the section as `// l3. Attach deep-link buttons to response message` (replacing "Send deep-link buttons as follow-up message").

    - If `finalize` deletes the message (empty text, short reply), the reply_markup is lost -- this is acceptable because short/empty replies with deep links are extremely rare.
    - If `finalize` splits a long message, reply_markup is skipped -- acceptable, long responses with deep links are uncommon.
