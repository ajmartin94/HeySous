<objective>
Add optimistic locking to all stateful household writes (knowledge items, meal plans, grocery lists) to prevent concurrent modifications from silently overwriting each other.

Purpose: When two household members (or even two rapid requests from the same user) modify the same data simultaneously, the second write should fail with a clear conflict message rather than silently winning. This is a simple mechanism for a rare event.

Output: Version columns on stateful tables, optimistic locking in repositories, conflict detection in tool handlers.
</objective>

1. **Knowledge repository** (`src/knowledge/repository.ts`):
   - Update `buildKnowledgeItem` to include `version` and `updatedBy` in the returned object
   - Update the `KnowledgeItem` type (in `src/knowledge/types.ts` if it exists, or wherever the type is defined) to include `version: number` and `updatedBy: string | null`
   - Update the `update()` method to accept an optional `expectedVersion` parameter:
     ```typescript
     update(id: number, householdId: string, changes: Record<string, unknown>, expectedVersion?: number): KnowledgeItem | null
     ```
     If `expectedVersion` is provided, add a WHERE clause: `AND version = expectedVersion`.
     On update, always increment `version` by 1 and set `updatedAt` to now.
     If `expectedVersion` is provided and 0 rows are affected, return `null` (conflict detected).
   - The `update()` method should also accept an optional `updatedBy` string and set it in the UPDATE.

2. **Plan repository** (`src/planning/repository.ts`):
   - Update `SavedPlan` to include `version: number` and `updatedBy: string | null`
   - Update `savePlan()` to accept an optional `expectedVersion` parameter:
     If a plan exists for the week and `expectedVersion` is provided, check the version matches before deleting entries and updating. If mismatch, return `null` (conflict).
     On save/update, always increment `version` and set `updatedAt` + `updatedBy`.

3. **Grocery repository** (`src/grocery/repository.ts`):
   - Update `GroceryList` interface to include `version: number` and `updatedBy: string | null`
   - Update the `mapList` helper to include `version` and `updatedBy`
   - Update write operations (`addItems`, `removeItems`, `checkItems`, `uncheckItems`) to accept an optional `expectedVersion` parameter. When provided:
     a. Before the write, check `SELECT version FROM grocery_lists WHERE id = ? AND version = ?`
     b. If no match, return a conflict indicator (e.g., throw a specific error or return false)
     c. After the write, increment the version: `UPDATE grocery_lists SET version = version + 1, updated_at = unixepoch() WHERE id = ?`

   The simplest approach: add an `updateListVersion(listId: number, expectedVersion: number): boolean` method that atomically checks and increments version. Tool handler calls this before writes.

4. **Tool handler** (`src/ai/tool-handler.ts`):
   - For `update_knowledge`: Read the item first (already done for changelog), pass `item.version` as `expectedVersion` to `knowledgeRepository.update()`. If update returns null, return a conflict error:
     ```json
     { "error": "This item was just modified by someone else. Please review the current version (use get_knowledge_item) and try your update again.", "is_error": true, "conflict": true }
     ```

   - For `save_meal_plan`: When an existing plan is found for the week, pass its version as `expectedVersion`. If savePlan returns null (conflict), return:
     ```json
     { "error": "The meal plan for this week was just updated by someone else. Please check the current plan (use get_meal_plan) and try again.", "is_error": true, "conflict": true }
     ```

   - For `update_grocery_list`: Before writing, call the version check method with `activeList.version`. If conflict detected, return:
     ```json
     { "error": "The grocery list was just updated by someone else. Please check the current list (use get_grocery_list) and try again.", "is_error": true, "conflict": true }
     ```

   - For `save_knowledge`, `delete_knowledge`: These don't need version checks. `save_knowledge` creates new items. `delete_knowledge` is a destructive action that doesn't race meaningfully.

   - Include version in tool responses where applicable so Claude sees the current version. For example, in `update_knowledge` success response, add `version: updated.version`. In `save_meal_plan` response, add `version: plan.version`. In `get_knowledge_item`, `get_meal_plan`, `get_grocery_list` responses, include the version field.

5. Pass `householdId` as `updatedBy` to repository methods (since tool handler already has householdId). This provides the edit metadata per locked decision.
