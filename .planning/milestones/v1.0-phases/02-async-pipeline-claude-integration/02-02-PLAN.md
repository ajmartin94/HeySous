<feature>
  <name>Message Debounce Queue</name>
  <files>src/pipeline/message-queue.ts, tests/pipeline/message-queue.test.ts</files>
  <behavior>
    The queue groups messages by chatId with a sliding debounce window.

    Debounce window: configurable, default 1500ms (per research recommendation).

    Behavior cases:
    - Single message, wait > window -> processFn called with batch containing 1 message
    - Two messages 500ms apart (within window) -> window resets, processFn called once with batch containing 2 messages
    - Three messages 400ms apart -> single batch of 3
    - Messages from different chatIds -> independent batches, processed separately
    - Batch deleted from internal map BEFORE processFn is called -> new messages during processing start a fresh batch (no double-processing)
    - Each message in batch has: text (string) and timestamp (Date)
    - Batch includes: chatId, userId, messages array, and the latest ctx reference

    Interface:
    ```typescript
    interface PendingBatch {
      chatId: string;
      userId: string;
      messages: Array<{ text: string; timestamp: Date }>;
      ctx: unknown; // BotContext in real usage, but queue is context-type-agnostic
    }

    type ProcessFn = (batch: PendingBatch) => Promise<void>;

    class MessageQueue {
      constructor(debounceMs?: number);
      enqueue(chatId: string, userId: string, text: string, ctx: unknown, processFn: ProcessFn): void;
      get pendingCount(): number; // For testing/monitoring
      shutdown(): void; // Clears all pending timers
    }
    ```

    The queue does NOT await processFn -- it fires and forgets (processing happens asynchronously).

    Test approach: Use vitest's fake timers (vi.useFakeTimers / vi.advanceTimersByTime) to control the debounce window precisely. Use a mock processFn (vi.fn()) to assert batch contents and call counts.
  </behavior>
  <implementation>
    Implement using a Map<string, PendingBatch & { timer: ReturnType<typeof setTimeout> }>.

    enqueue():
    1. Check if chatId exists in map
    2. If yes: clearTimeout on existing timer, push new message, update ctx to latest
    3. If no: create new entry with first message
    4. Set new timer: on expiry, DELETE entry from map first, THEN call processFn(batch)
       - Delete-before-process prevents the double-processing race condition (Pitfall 3 from research)
       - processFn is called with .catch() to log but not throw -- queue must not crash on processor errors

    shutdown():
    - Iterate map, clearTimeout on all entries, clear the map
    - Used for graceful shutdown and test cleanup

    Export both the MessageQueue class and a convenience `createMessageQueue(debounceMs?)` factory.
  </implementation>
</feature>
