**src/ai/tool-handler.ts** -- Add handler cases for new memory tools and rename settings handlers:

1. `save_memory` case:
   - Validate input: content (string, max 2000 chars), category (string from enum)
   - If `update_id` provided: call `updateMemory(sqlite, update_id, input.content)`, return success message
   - If `skip_dedup` not true: call `searchMemoryFts(sqlite, householdId, input.content, 5)` to find similar memories
   - If matches found with rank above threshold (use -5.0 as FTS5 rank threshold -- more negative = better match, so check `rank < -5.0`): return JSON with `{ status: "dedup_match", matches: [...] }` so Claude can decide ADD/UPDATE/NOOP in a follow-up call
   - If no matches or skip_dedup: call `saveMemory(sqlite, householdId, input.content, input.category)`, return `{ status: "saved", id, content, category }`

2. `delete_memory` case:
   - Call `deleteMemory(sqlite, input.id, householdId)`, return success/failure

3. `search_memories` case:
   - Call `searchMemoryFts(sqlite, householdId, input.query, input.limit || 10)`, return results array

4. Rename `update_reminder_settings` case to `update_settings` and `get_reminder_settings` to `get_settings`. Update the SQL queries inside these handlers to reference `application_settings` instead of `reminder_settings`.

5. Update `save_knowledge` handler: In the description comment, note that preferences should now use `save_memory` instead. The handler itself stays unchanged (recipes still go through save_knowledge).

Import `saveMemory`, `updateMemory`, `deleteMemory`, `getMemoryById` from `../memory/repository.js` and `searchMemoryFts` from `../memory/fts.js`.

**src/ai/system-prompt.ts** -- Replace preference injection with memory injection:

1. Replace `buildPreferenceContext(preferences: PreferenceSummary[])` with `buildMemoryContext(memories: Array<{ id: number; content: string; category: string }>)`:
   - Group memories by category
   - Format as categorized XML block `<user_memories>` with category sections
   - Preserve severity markers: if content starts with "[ALLERGY]" or "[RESTRICTION]", keep those as hard constraint markers in the injection
   - Use the same hard/soft constraint framing as current preference context
   - Inject up to ~100 memories (soft limit); if more exist, add a note: "Additional memories available via search_memories tool"

2. Update the function signature of `buildDynamicContext` (or wherever preferences are passed in) to accept memories instead of PreferenceSummary[]. Grep for all call sites and update.

3. Add memory-saving instructions to the system prompt static section:
   ```
   <memory_instructions>
   You have a long-term memory system. Save durable facts about the user proactively:
   - Dietary needs, allergies, restrictions (category: dietary)
   - Taste preferences, liked/disliked ingredients (category: taste)
   - Cooking style, equipment, skill level (category: cooking_style)
   - Household members, who eats what (category: household)
   - Meal time preferences, schedule constraints (category: schedule)
   - Store preferences, budget, delivery preferences (category: logistics)

   Save silently -- never say "I'll remember that" or ask "should I save this?"
   Skip transient information (today's mood, one-time requests).
   For settings changes (meal times, timezone), call BOTH save_memory AND update_settings.
   </memory_instructions>
   ```

4. Remove the `PreferenceSummary` import and `buildPreferenceContext` function entirely. Remove any reference to `getPreferenceSummaries`.
