**1c. Add `streamMessageWithTools` method to the claude client in `src/ai/claude-client.ts`:**

Add a new method to the client object returned by `createClaudeClient`. This method uses the Anthropic SDK's `client.messages.stream()` API instead of `client.messages.create()`.

The method signature:
```typescript
streamMessageWithTools(
  messages: Anthropic.MessageParam[],
  tools: Anthropic.Tool[],
  onToolCall: (name: string, input: Record<string, unknown>) => string | Promise<string>,
  callbacks: {
    onText?: (textDelta: string, textSnapshot: string) => void;
    onToolUseStart?: (toolName: string) => void;
    onToolUseEnd?: (toolName: string) => void;
  },
  maxIterations?: number,
  systemPrompt?: SystemPromptInput,
  onRetry?: (attempt: number, delayMs: number) => void | Promise<void>,
): Promise<ClaudeResponse>
```

Implementation approach:
- Use `client.messages.stream(params)` which returns a `MessageStream`
- Register `stream.on('text', (delta, snapshot) => callbacks.onText?.(delta, snapshot))` for text deltas
- When stream completes (`await stream.finalMessage()`), check for tool_use blocks in the final message
- If tool_use blocks are present, execute tool calls (same as non-streaming), then start a NEW stream iteration with the tool results appended
- The tool use loop logic follows the same pattern as `sendMessageWithTools` but each iteration uses `.stream()` instead of `.create()`
- Call `callbacks.onToolUseStart?.(toolName)` before executing each tool, and `callbacks.onToolUseEnd?.(toolName)` after
- Aggregate token usage across all stream iterations from `finalMessage().usage`
- Wrap each stream call in `retryWithBackoff` for 429 handling -- wrap the entire stream creation + await finalMessage in the retry function
- Use `maxIterations` (default `DEFAULT_MAX_ITERATIONS`) same as non-streaming
- Safety valve: if max iterations reached, do one final stream WITHOUT tools to force text response
- Return the same `ClaudeResponse` shape with aggregated usage

Important: The `stream.on('text', ...)` callback fires for EVERY text delta in the current iteration. When a tool use loop has multiple iterations, only the LAST iteration's text should be streamed to the user (earlier iterations may have partial text before tool calls -- those are Claude's internal reasoning). To handle this: only register the `onText` callback on the final stream (the one that produces end_turn without tool_use blocks). For tool-use iterations, skip the `onText` registration but still call `onToolUseStart`/`onToolUseEnd`.

Wait -- actually the Anthropic streaming API fires text events as they arrive, and we don't know in advance if this iteration will end with tool_use or end_turn. The approach should be:
1. Always register `onText` callback on every stream iteration
2. If the iteration ends with tool_use (meaning there WILL be more iterations), the processor/bridge will handle clearing the partial text and showing tool status instead
3. The `onToolUseStart` callback signals that the current text should be preserved (it's Claude's preamble before tool use) and tool status should be shown

Actually, simplest approach: always stream text, let the bridge handle the display. The bridge knows how to append cursor, show tool status, etc. This keeps the claude-client focused on the API interaction and the bridge focused on display.

So the final approach:
- Register `onText` on every iteration
- Fire `onToolUseStart` before each tool call
- Fire `onToolUseEnd` after each tool call
- Let the caller (bridge) manage what to show

Create `src/telegram/stream-sender.ts` -- a module that manages the lifecycle of a streaming Telegram message.

Export a factory function `createTelegramStreamSender(ctx: BotContext, logger: Logger)` that returns an object with methods:

```typescript
interface TelegramStreamSender {
  // Called once to send the initial placeholder message (just the cursor ▍)
  sendPlaceholder(): Promise<void>;

  // Called on each text delta from the Claude stream
  appendText(delta: string): void;

  // Called when a tool starts executing -- shows status label inline
  showToolStatus(label: string): void;

  // Called when a tool finishes -- clears the status, ready for more text
  clearToolStatus(): void;

  // Called when the stream is complete -- sends the final clean message
  // Returns the final text that was displayed
  finalize(): Promise<string>;

  // Called on stream error -- appends error note to partial text
  handleError(): Promise<string>;
}
```

**Internal state:**
- `messageId: number | null` -- the Telegram message ID of the streamed message (set after sendPlaceholder)
- `chatId: string` -- from `ctx.chat!.id`
- `accumulatedText: string` -- all text received so far
- `currentToolStatus: string | null` -- current tool status label (if any)
- `lastEditText: string` -- the text of the last successful edit (to avoid no-op edits)
- `lastEditTime: number` -- timestamp of last successful edit

**Cursor constant:** `const CURSOR = "▍";`

**sendPlaceholder():**
- Send a new message with just the CURSOR via `ctx.reply(CURSOR, { parse_mode: undefined })` (plain text, no HTML parsing for the cursor)
- Store the returned `message_id` in `messageId`
- Also start the typing indicator via `ctx.replyWithChatAction("typing")` (belt and suspenders per locked decision)

**appendText(delta):**
- Append `delta` to `accumulatedText`
- Call the internal `_scheduleEdit()` method

**_scheduleEdit() (internal):**
- Use a time-based pacing strategy: edits at most every 300ms (Claude's discretion -- 300ms balances responsiveness with Telegram rate limits)
- If less than 300ms since `lastEditTime`, set a timer to fire at the 300ms mark (debounce pattern)
- When the timer fires or enough time has passed, call `_doEdit()`

**_doEdit() (internal):**
- Build the display text:
  - If `currentToolStatus` is set: `accumulatedText + "\n\n<i>" + toolStatus + "</i>" + CURSOR`
  - Else: `accumulatedText + CURSOR`
- If display text equals `lastEditText`, skip (no-op optimization)
- Call `ctx.api.editMessageText(chatId, messageId, displayText, { parse_mode: undefined })` -- use PLAIN TEXT during streaming to avoid HTML parsing errors on partial content (Claude's discretion)
- On success: update `lastEditText` and `lastEditTime`
- On failure (GrammyError or any error): log at debug level and skip (per locked decision -- user sees a text jump but no error). Do NOT throw.
- Also send `ctx.replyWithChatAction("typing")` periodically (every ~4 seconds) to keep the typing indicator alive alongside the streamed message

**showToolStatus(label):**
- Set `currentToolStatus = label`
- Trigger an immediate `_doEdit()` to show the status right away

**clearToolStatus():**
- Set `currentToolStatus = null`
- (Don't trigger edit -- next text delta will update)

**finalize():**
- Flush any pending edit timer
- If `accumulatedText.trim().length === 0`, delete the placeholder message (nothing to show) and return ""
- If `accumulatedText.trim().length < 50` (short reply per locked decision):
  - Delete the streamed message (the one with cursor/partial edits)
  - Send a fresh message via `sendFormattedMessage(ctx, accumulatedText)` for clean HTML formatting
  - Return `accumulatedText`
- Otherwise (normal/long reply):
  - For messages under 4096 chars: do a final `editMessageText` with the clean text (no cursor) using `parse_mode: "HTML"` for proper formatting. If HTML edit fails, fall back to plain text edit.
  - For messages over 4096 chars (need splitting): delete the streamed message, then use `sendFormattedMessage(ctx, accumulatedText)` which handles splitting. This avoids the complexity of streaming across multiple messages.
  - Return `accumulatedText`

**handleError():**
- Flush any pending edit timer
- Append " <i>(response interrupted -- try again)</i>" to `accumulatedText` (per locked decision, HTML italic)
- Do a final edit with `parse_mode: undefined` (plain text fallback -- the italic tag won't render but the message is readable)
- Actually, since we use plain text during streaming, just append "(response interrupted -- try again)" without HTML tags
- Return `accumulatedText`

**Typing indicator keep-alive:**
- Use a setInterval(4000) that calls `ctx.replyWithChatAction("typing")` wrapped in try/catch
- Start the interval in `sendPlaceholder()`
- Clear the interval in `finalize()` and `handleError()`

**Important implementation notes:**
- All Telegram API calls (editMessageText, replyWithChatAction) must be wrapped in try/catch -- failures are logged and skipped, never thrown
- Use `parse_mode: undefined` during streaming to avoid HTML parse errors on partial Claude output
- The final edit in `finalize()` is the only one that uses `parse_mode: "HTML"`
- Import `sendFormattedMessage` from `./sender.js` for the finalize path that needs splitting
- Import `splitMessage` from `./splitter.js` if needed for length checking
