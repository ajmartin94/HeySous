<task type="auto">
  <name>Task 1: Create onboarding module (state machine and prompt builder)</name>
  <files>src/onboarding/state.ts, src/onboarding/prompt.ts</files>
  <action>
Create `src/onboarding/state.ts`:

- Export `OnboardingState` type: `"preferences" | "tour" | "recipes" | "tour_only" | "complete"` (drop "registered" and "new_household"/"joining_household" -- those are transient states handled by the start handler, not stored)
- Export `ONBOARDING_STATES` array for validation
- Export `getNextOnboardingState(current: OnboardingState, completedPhase: string): OnboardingState`:
  - If completedPhase === "skip" -> return "complete" (from ANY state)
  - "preferences" completed -> "tour"
  - "tour" completed -> "recipes"
  - "recipes" completed -> "complete"
  - "tour_only" completed -> "complete" (for tour phase name "tour")
  - Default: return current (no-op for unknown phases)
- Export `extractOnboardingMarker(text: string): { text: string; completedPhase: string | null }`:
  - Match `/__ONBOARDING_PHASE_COMPLETE:(\w+)__/`
  - If found: return cleaned text (marker removed, trimmed) and the captured phase name
  - If not found: return original text and null
  - IMPORTANT: Handle marker on its own line (may have leading newlines). Strip the marker AND any trailing/leading blank lines it leaves behind.

Create `src/onboarding/prompt.ts`:

- Export `buildOnboardingPrompt(state: OnboardingState): string`
- Returns empty string for "complete" state
- For each state, return an `<onboarding>` XML section with Claude instructions:

**"preferences" state** (~150 words):
- You are getting to know a new user. This is your first conversation with them.
- YOUR GOAL: Learn about their household's food preferences through natural conversation.
- Ask about: dietary restrictions/allergies (save with severity:allergy/severity:restriction tags), taste preferences and likes/dislikes, what time they usually have dinner (save as preference AND call update_reminder_settings), where they shop for groceries (save with pref:grocery tag), cooking comfort level.
- CONVERSATION STYLE: Chat like getting to know a friend, not filling out a form. Ask 1-2 questions at a time, not a big list. Save preferences as you learn them using save_knowledge (don't wait until the end). When you've covered the main topics, naturally transition to showing them what you can do.
- SKIP HANDLING: If user says "skip", "skip this", "just let me use it", or similar: send a brief capabilities summary mentioning both chatting with Sous for meal planning AND using the mini-app for quick reference (grocery lists, recipes, meal plans), then include the skip marker. Do NOT make them feel bad about skipping.
- WHEN DONE: Include `__ONBOARDING_PHASE_COMPLETE:preferences__` on its own line at the very end of your message. The user will NOT see this marker.

**"tour" state** (~80 words):
- The user just finished sharing their preferences. Now show them what you can do.
- Send a single message listing key capabilities. Mention: meal planning (weekly dinner plans), recipe management (save, search, modify recipes), grocery lists (auto-generated from meal plans), prep reminders (morning summaries, cooking nudges), AND the mini-app for quick reference (grocery lists, recipes, meal plans on their phone).
- Keep it brief and enthusiastic, not a manual.
- After sending the tour, include `__ONBOARDING_PHASE_COMPLETE:tour__` on its own line.
- SKIP HANDLING: Same as preferences state.

**"recipes" state** (~80 words):
- The user has seen the tour. Now encourage them to teach you some recipes.
- Prompt naturally: something like asking them to tell you about meals they make regularly. They describe freely, you extract and save recipes using save_knowledge.
- No minimum count -- if they want to stop or say "that's it" or similar, wrap up warmly.
- Do NOT gate progress on recipe count. If user teaches 0 recipes, that is fine.
- WHEN DONE (user says they're done, or conversation naturally wraps): Include `__ONBOARDING_PHASE_COMPLETE:recipes__` on its own line.
- SKIP HANDLING: Same as preferences state.

**"tour_only" state** (~60 words):
- This user joined an existing household. They don't need preference questions or recipe seeding.
- Send the same capability tour as the "tour" state (mention chat + mini-app).
- After sending, include `__ONBOARDING_PHASE_COMPLETE:tour__` on its own line.
- SKIP HANDLING: Same as other states.

ALL states must include: "If the user goes off-topic during onboarding, roll with it naturally -- answer their request, then gently steer back to what you were discussing." and "Do NOT use step indicators, emoji headers, or anything that looks different from a normal conversation."

Use .js extension on all local imports. Follow existing ESM patterns.

  <name>Task 2: Expand users data layer for onboarding states</name>
  <files>src/users/types.ts, src/users/init.ts, src/users/repository.ts</files>
  <action>
Update `src/users/types.ts`:
- Change `onboardingState` on both `User` interface and `CreateUserParams` to: `"preferences" | "tour" | "recipes" | "tour_only" | "complete"` (import from onboarding/state.ts or redefine -- keeping it self-contained in types.ts is fine since it's the canonical type).
- Remove "registered" from the union -- it is no longer used.

Update `src/users/init.ts`:
- The CHECK constraint currently reads: `CHECK(onboarding_state IN ('registered', 'complete'))`
- SQLite does not support ALTER CHECK constraints. For existing databases, we need a table rebuild.
- Add a migration function `migrateOnboardingEnum(sqlite)` called from `initializeUsers` AFTER the CREATE TABLE IF NOT EXISTS:
  1. Check current CHECK constraint: `SELECT sql FROM sqlite_master WHERE name = 'users' AND type = 'table'` -- if the sql contains `'registered'` but NOT `'preferences'`, migration is needed.
  2. If migration needed, run in a transaction:
     - `CREATE TABLE users_new (...)` with the full schema including the NEW CHECK constraint: `CHECK(onboarding_state IN ('preferences', 'tour', 'recipes', 'tour_only', 'complete'))`
     - `INSERT INTO users_new SELECT ... FROM users` (mapping 'registered' to 'complete' for any existing users with that state)
     - `DROP TABLE users`
     - `ALTER TABLE users_new RENAME TO users`
  3. If the table was just created fresh (no data), the CREATE TABLE already has the new constraint -- no migration needed.
- Update the CREATE TABLE IF NOT EXISTS to use the new CHECK constraint with expanded values.
- Update the default value from 'registered' to 'complete' (new users get set explicitly by the start handler; the default is a safety fallback).
- Keep the admin seed as onboarding_state='complete' (unchanged).

Update `src/users/repository.ts`:
- Add `updateOnboardingState(sqlite, telegramId, newState)` function:
  - Takes `BetterSqlite3.Database`, `telegramId: string`, `newState: User["onboardingState"]`
  - Runs: `UPDATE users SET onboarding_state = ?, updated_at = unixepoch() WHERE telegram_id = ?`
  - Returns the updated User (re-read from DB after update) or undefined if not found.
- Follow existing standalone function export pattern (not factory).

IMPORTANT: Ensure the migration handles the case where the users table has NO "registered" users (all are "complete") -- the table rebuild should still update the CHECK constraint even if no data rows need changing.
