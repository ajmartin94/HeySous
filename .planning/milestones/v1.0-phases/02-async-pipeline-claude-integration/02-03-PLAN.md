  <name>Task 1: Create pipeline processor with retry, timeout, and token logging</name>
  <files>
    src/pipeline/processor.ts

  <action>
    1. Create `src/pipeline/processor.ts`:
       Export a factory `createProcessor(deps)` that accepts dependencies (claude client, db instance, logger) and returns a `processBatch(batch: PendingBatch)` async function.

       The processBatch function implements the full pipeline per locked user decisions:

       a. **Start typing indicator**: Call `ctx.replyWithChatAction("typing")` on the batch's ctx to show "typing..." while processing. Wrap in try/catch -- typing indicator failure should not block processing.

       b. **Build user message**: Join all batch messages' text with `"\n\n"` (preserving multi-message context).

       c. **30-second timeout warning**: Start a timer that after 30,000ms sends "This is taking longer than usual, hang tight..." via `ctx.reply()`. Per locked decision: timeout messaging at 30s.

       d. **Attempt 1 -- call Claude**: Call the claude client's sendMessage with the user messages array. If it succeeds, clear the timeout timer and proceed to step (f).

       e. **Attempt 2 -- silent retry**: If attempt 1 throws, log the error at warn level with full error details, request context, userId, and timestamp (per locked decision: detailed error logging). Retry once. If attempt 2 succeeds, clear timeout timer and proceed to step (f). If attempt 2 also throws, clear timeout timer, log at error level with full details, and send the in-character error message: "Sorry, I'm having trouble thinking right now. Try again in a moment!" via ctx.reply(). Return early.

       f. **Send response**: Use `sendFormattedMessage(ctx, response.text)` from `src/telegram/sender.ts` to deliver Claude's formatted response with HTML fallback and message splitting.

       g. **Log token usage to database**: Insert a row into the tokenUsage table with:
          - chatId and userId from the batch
          - model from the Claude response
          - conversationType: "chat" (hardcoded for Phase 2, expanded in later phases)
          - inputTokens, outputTokens, cacheCreationTokens, cacheReadTokens from response.usage
          - estimatedCost calculated via calculateCost()
          - requestDurationMs: measure elapsed time from before the Claude call to after

       h. **Log token usage to pino**: Log at info level a structured object with: chatId, userId, model, inputTokens, outputTokens, cacheCreationTokens, cacheReadTokens, estimatedCost, requestDurationMs, conversationType. Use message: "Claude API call completed". This satisfies the requirement for token usage visible in logs.

       i. **Outer try/catch**: Wrap the entire processBatch in a try/catch that logs unexpected errors at error level and attempts to send the in-character error message. The processor must NEVER throw -- it's called from the debounce queue's fire-and-forget pattern.

    2. Create `src/bot/handlers/costs.ts`:
       Export `costsHandler` as a Composer<BotContext>.

       Register a `/costs` command handler that:
       a. Checks if `ctx.from?.id` (as string) is in `config.adminUserIds`. If not, return silently (no response -- per locked decision: only visible to admin users).
       b. Query the tokenUsage table for aggregates:
          - Total requests (count)
          - Total cost (sum of estimatedCost)
          - Total input tokens, output tokens
          - Cache hit rate: sum(cacheReadTokens) / (sum(inputTokens) + sum(cacheReadTokens)) * 100, or 0 if no data
          - Optionally: today's cost and this month's cost
       c. Reply with an HTML-formatted summary message:
          ```
          <b>Usage Summary</b>

          Total requests: {N}
          Total cost: ${X.XXXX}
          Input tokens: {N}
          Output tokens: {N}

          <b>Cache</b>
          Cache reads: {N} tokens
          Cache writes: {N} tokens
          Hit rate: {X.X}%
          ```

       The costs handler needs database access. Accept it via a closure: export a function `createCostsHandler(db)` that returns the Composer. Alternatively, read db from a module-level reference set during initialization (follow whichever pattern is established in Plan 01's wiring).

       NOTE: The costs handler needs access to the database. The approach for injecting the db will be to pass it when creating the handler (factory pattern consistent with createBot, createProcessor, etc.). See Task 2 for wiring.
  </action>

  </verify>

    2. Update `src/bot/handlers/message.ts`:
       Replace the echo handler with the async enqueue pattern:
       ```typescript
       messageHandler.on("message:text", (ctx) => {
         const chatId = String(ctx.chat.id);
         const userId = String(ctx.from?.id ?? "unknown");
         const text = ctx.message.text;
         // Enqueue and return immediately -- do NOT await Claude here
         // The queue reference will be set via a module-level setter (see below)
         queue.enqueue(chatId, userId, text, ctx, processBatch);
       });
       ```

       For dependency injection of the queue and processBatch function into the message handler, use one of these approaches (pick the simplest that works):
       - Option A: Export a `setMessagePipeline(q: MessageQueue, fn: ProcessFn)` function that sets module-level references, called from main.ts during init
       - Option B: Make `createMessageHandler(queue, processBatch)` a factory that returns the Composer
       - Option B is preferred (consistent with createBot/createProcessor factory pattern)

       CRITICAL: The message:text handler must NOT await anything slow. It calls `queue.enqueue()` (synchronous) and returns. This is what prevents Telegram webhook timeouts (requirement INFRA-02).

    3. Update `src/bot/index.ts`:
       - Accept additional parameters for the message handler dependencies (queue, processBatch) OR accept a pre-built message handler
       - Register the costs handler BEFORE the message handler (commands must be matched before the catch-all message handler)
       - Update createBot signature: `createBot(token, options: { costsHandler, messageHandler })` or similar pattern that allows injecting the configured handlers
       - Keep existing middleware order: hydrateReply -> autoChatAction -> commands (start, costs) -> message handler -> error boundary

    4. Update `src/main.ts` to wire everything together:

       c. `const queue = createMessageQueue()` -- new, uses default 1500ms debounce
       d. `const processBatch = createProcessor({ claudeClient, db, logger })` -- new

       g. Inject db into bot context via middleware: `bot.use((ctx, next) => { ctx.db = db; return next(); })` -- place BEFORE handlers that need it
