<objective>
Create the runtime reminder engine: a poller that checks for due reminders every 60 seconds and a sender that delivers them via Telegram with Claude-generated text.

Purpose: This is the heart of proactive messaging -- the poller runs continuously, finds reminders that are due, generates persona-consistent text via Claude, and sends them to users via bot.api.sendMessage. It's designed to be crash-safe (mark sent before delivery attempt) and restart-safe (process overdue on startup). The sender fetches recipe content for prep alerts so Claude can analyze what needs advance preparation.
Output: Sender module (text generation + recipe analysis + delivery) and poller module (interval loop + query + dispatch).
</objective>

Use minimal interface types for bot, claudeClient, and retrievalService deps (not full types) to keep the sender decoupled. Import Logger from pino.

**IMPORTANT -- retrievalService is required.** Per user decision, Claude must analyze actual recipe content to determine prep needs. The sender uses `retrievalService.getItem(knowledgeItemId, chatId)` to fetch recipe content for prep_alert reminders.

Returns object with:

**`sendReminder(reminder: Reminder): Promise<boolean>`**

1. Parse `reminder.contextJson` to get meal context
2. Generate varied reminder text via Claude:
   - Build a focused system prompt for reminder text generation (NOT the full Sous prompt):
     ```
     You are Sous, a warm and friendly kitchen assistant. Write a brief, casual reminder message for Telegram.
     Keep it to 1-2 short sentences. Use HTML formatting (<b>, <i>) sparingly.
     Be varied -- don't use the same phrasing every time. Sound like a friendly kitchen buddy, not a calendar alarm.
     Do NOT use markdown. Do NOT use emojis excessively. Keep it natural.
     ```
   - User message describes what reminder to write based on type:
     - `morning_summary`: If context has meals: "Write a morning prep summary for today. Meals planned: {list of meals with types}. {any prep notes if available}. Keep it like a sticky note on the fridge -- 2-3 lines max." If context has `type: "no_plan_nudge"`: "Write a brief, casual nudge that there's no dinner planned for tonight ({date}). Something like 'No dinner planned for tonight -- want to pick something?' Keep it to one sentence, friendly not guilt-trippy."
     - `prep_alert`: **Fetch the actual recipe content** using `retrievalService.getItem(context.knowledgeItemId, reminder.chatId)`. If recipe found, include the full recipe content in the prompt: "Analyze this recipe and write a brief prep reminder. The recipe '{recipeName}' is planned for {mealDate} ({mealType}). Here is the full recipe:\n\n{recipeContent}\n\nBased on the recipe, determine what needs advance preparation (defrosting, marinating, soaking, brining, etc.) and write a brief heads-up. Just the what and when -- no instructions. One or two sentences." If recipe NOT found (knowledge item deleted or missing), fall back to generic: "Write a brief prep reminder for '{recipeName}' planned for {mealDate}. Remind them to check if anything needs advance prep. One sentence."
     - `start_cooking`: "Write a start-cooking nudge. Tonight's dinner is '{recipeName}'. Keep it to one casual sentence."
   - Call `claudeClient.sendMessage([userMessage], reminderSystemPrompt)`
3. Send via `bot.api.sendMessage(reminder.chatId, generatedText, { parse_mode: "HTML" })`
4. Return true on success, false on failure

**Error handling:**
- If Claude API fails, use plain-text fallback:
  - morning_summary (with meals): "Good morning! Here's what's on the menu today: {meal list}"
  - morning_summary (no_plan_nudge): "No dinner planned for tonight -- want to pick something?"
  - prep_alert: "Heads up -- {recipeName} is on tomorrow's menu. Check if anything needs advance prep!"
  - start_cooking: "Time to start cooking! Tonight: {recipeName}"
- If Telegram sendMessage fails with 403 (bot blocked), log a warning and return false. Do NOT retry.
- If Telegram sendMessage fails with other error, log error and return false.
- Wrap entire function in try/catch -- sender must NEVER throw.

Log each send attempt at info level with chatId, reminder type, and success/failure.


Import types from ./types.js and type for createReminderRepository from ./repository.js.

Returns object with:

**`start(): void`**
- Log "Reminder poller started (60s interval)" at info level
- Process any overdue reminders immediately on start (call `tick()` once)
- Set up `setInterval(tick, 60_000)` -- 60 second interval
- Store the interval reference for cleanup

**`stop(): void`**
- Clear the interval
- Log "Reminder poller stopped" at info level

**`async tick(): Promise<void>`** (can be called directly for testing)
- Query `reminderRepository.getDueReminders()` for all pending reminders where due_at <= now
- If no due reminders, return immediately (no logging to avoid noise)
- For each due reminder:
  1. **Mark as sent FIRST** (before attempting delivery) -- call `reminderRepository.markSent(reminder.id, "")` with empty text. This prevents duplicates if the process crashes during send. Per research pitfall: mark BEFORE send, not after.
  2. Call `sender.sendReminder(reminder)`
  3. If send succeeds, update with actual generated text: `reminderRepository.markSent(reminder.id, generatedText)` -- actually, markSent was already called. Instead, do a simpler approach: markSent sets status only, then update generated_text separately. **Revised approach:** Call markSent with a placeholder first. If sender returns the generated text, update it. OR simpler: just mark sent with empty string before send, the text is fire-and-forget anyway.
  4. If send fails, call `reminderRepository.markFailed(reminder.id)` -- override the premature markSent. This way, on restart, failed reminders are NOT retried (they're marked failed, not pending). Per user decision: fire and forget, no re-reminders.
  5. Log each processed reminder at info level with id, type, chatId, success/failure

- Wrap entire tick in try/catch -- poller must NEVER crash. Log errors at error level.
- Process reminders sequentially (not in parallel) to avoid overwhelming Telegram rate limits.

**Revised send flow (cleaner):**
1. Mark status as 'sent' immediately to prevent re-processing
2. Attempt send
3. If send fails, mark as 'failed' (overrides 'sent')
4. If send succeeds, optionally update generated_text (cosmetic, for debugging/logging)

Actually, simplest correct approach: change markSent to accept generatedText. In the flow:
1. Set status='sent' and generated_text='' BEFORE attempting send
2. Call sender.sendReminder(reminder) which returns boolean
3. If failed, update status to 'failed'
4. The generated text is ephemeral anyway -- no need to store it back

This keeps the repository API clean and the flow safe against duplicates.
