<objective>
Add preference retrieval, system prompt preference injection, and processor integration so that user preferences (stored as knowledge items tagged "preference") are proactively loaded and applied as constraints in every Claude call.

Purpose: This is the core infrastructure for Phase 5. Without proactive preference loading into the system prompt, Claude cannot reliably apply dietary restrictions and other constraints -- it would need to remember to search for preferences every turn, which is unreliable. This plan ensures preferences are always visible to Claude.

Output: Working preference-aware pipeline where preferences stored via existing knowledge tools appear in the system prompt on the next message, influencing Claude's behavior.
</objective>

Create `src/knowledge/preferences.ts` with:

1. Export a `PreferenceSummary` interface:
   ```typescript
   export interface PreferenceSummary {
     id: number;
     title: string;
     summary: string;
     tags: string[];
   }
   ```

2. Export a `getPreferenceSummaries` function that takes `(sqlite: BetterSqlite3.Database, chatId: string, limit: number = 30)` and returns `PreferenceSummary[]`. Use raw SQLite (same pattern as `fts.ts` -- NOT Drizzle) with an efficient JOIN query:
   ```sql
   SELECT DISTINCT ki.id, ki.title, ki.summary
   FROM knowledge_items ki
   JOIN knowledge_tags kt ON kt.knowledge_item_id = ki.id
   WHERE ki.chat_id = ? AND kt.tag = 'preference'
   ORDER BY ki.last_accessed_at DESC
   LIMIT ?
   ```
   Then fetch tags for each result using a prepared statement (same pattern as `searchFts` in `fts.ts`). Return array of `PreferenceSummary` objects.

3. Use `.js` extension on all local imports (ESM convention).
4. Import `type BetterSqlite3 from "better-sqlite3"` for the type only.

Then modify `src/ai/system-prompt.ts`:

1. Import `type { PreferenceSummary } from "../knowledge/preferences.js"`.

2. Change `buildSystemPrompt()` signature to `buildSystemPrompt(preferences?: PreferenceSummary[]): string`.

3. Add a `buildPreferenceContext(preferences: PreferenceSummary[]): string` helper function that:
   - If preferences array is empty/undefined, returns empty string.
   - Otherwise formats each preference as a line: `- {title}{markers}: {summary}`
   - Markers: `[ALLERGY]` if tags include `severity:allergy`, `[RESTRICTION]` if tags include `severity:restriction`, `[inferred]` if tags include `inferred`.
   - Wraps in `<user_preferences>` XML tags with instructions about hard constraints (allergy/restriction) vs soft preferences.

4. Add a `PREFERENCE_MANAGEMENT_PROMPT` constant string containing the always-present preference management instructions. This section teaches Claude:
   - How to detect preferences (explicit and inferred)
   - How to save them using save_knowledge with the `preference` base tag plus domain tags (pref:dietary, pref:schedule, pref:cooking, pref:household, pref:budget, pref:serving, pref:grocery), subject tags (subject:self, subject:household), severity tags (severity:allergy, severity:restriction), and optional `inferred` tag
   - Acknowledgment style: brief and natural ("Noted: no pork.") then continue conversation -- NO confirmation step
   - IMPORTANT: search for existing similar preferences before saving to avoid duplicates
   - How to apply preferences from `<user_preferences>` as constraints
   - Conflict handling: flag tension between conflicting preferences, warn-and-comply for allergy overrides
   - How to update and delete preferences conversationally
   - How to present preferences when asked ("what do you know about me?")
   - Inferred preference guidance: conservative (3+ instances), acknowledge as inference, tag with `inferred`

5. Append both `buildPreferenceContext(preferences)` and `PREFERENCE_MANAGEMENT_PROMPT` to the end of the system prompt string returned by `buildSystemPrompt()`. The preference management instructions are ALWAYS appended (even when no preferences exist yet) so Claude knows how to handle preference capture from the first message.

IMPORTANT: The existing recipe_management section in the system prompt must NOT be modified. The preference_management section is a NEW, SEPARATE section appended after recipe_management.
