**In `src/pipeline/processor.ts`:**
Create a function `createInstrumentedToolHandler` that wraps `toolHandler.handleToolCall`. This wrapper:
1. Records `Date.now()` before calling the underlying handler
2. Calls `handleToolCall(name, input)` inside a try/catch
3. On success:
   - Computes `duration_ms = Date.now() - startTime`
   - Logs via Pino at `info` level: `{ tool_name: name, duration_ms, household_id: householdId, status: "success" }` with message `"Tool call completed"`
   - If `config.logToolInputs` is true, also include `tool_input: input` in the log object
   - Returns the result string unchanged
4. On error (thrown exception):
   - Computes `duration_ms`
   - Logs via Pino at `error` level: `{ tool_name: name, duration_ms, household_id: householdId, status: "error", error: errorMessage, tool_input: input }` -- ALWAYS include `tool_input` on errors regardless of LOG_TOOL_INPUTS
   - Re-throws the error (let claude-client.ts handle it for Claude)

Then, in the `processBatch` function, instead of passing `toolHandler.handleToolCall` directly to `sendMessageWithTools`, wrap it:

```typescript
const instrumentedHandler = createInstrumentedToolHandler(
  toolHandler.handleToolCall,
  householdId,
  log,
);
```

Replace **both** occurrences of `toolHandler.handleToolCall` in `processBatch` — both the first attempt and the retry attempt — with `instrumentedHandler`. Pass `instrumentedHandler` to `claudeClient.sendMessageWithTools` in both call sites.

Note: The wrapper function signature must match `(name: string, input: Record<string, unknown>) => string | Promise<string>` so it can be passed directly.

**In `src/ai/claude-client.ts`:**
Add a helper function `sanitizeToolError`:
```typescript
function sanitizeToolError(error: unknown): string {
  const raw = error instanceof Error ? error.message : String(error);
  // Strip stack traces, file paths, and SQL from the message
  const sanitized = raw
    .replace(/\s+at\s+.+/g, "")           // stack trace lines
    .replace(/\/[\w/.-]+\.\w+/g, "[path]") // file paths like /src/foo/bar.ts
    .replace(/(SELECT|INSERT|UPDATE|DELETE|CREATE|ALTER|DROP)\s+.*/gi, "[sql]") // SQL statements
    .trim();
  return sanitized || "An internal error occurred";
}
```

Then update the tool result catch block in `sendMessageWithTools` (the `catch (error)` inside the `Promise.all` for tool results) to use `sanitizeToolError`:
```typescript
catch (error) {
  return {
    type: "tool_result" as const,
    tool_use_id: block.id,
    content: JSON.stringify({ error: sanitizeToolError(error) }),
    is_error: true,
  };
}
```

This ensures Claude never sees raw stack traces, file paths, or SQL in tool error results.

**Per locked decisions:**
- Two-tier error flow: descriptive errors for Claude's internal retry logic (tool name + what failed), generic errors for user-facing messages. The processor already handles user-facing errors via `getErrorMessage()`.
- Structured tool call logs via Pino to stdout (no SQLite persistence, no new log destinations).
- Full tool input parameters logged on error only (not on success by default).
- LOG_TOOL_INPUTS env toggle to enable full input logging on success.
