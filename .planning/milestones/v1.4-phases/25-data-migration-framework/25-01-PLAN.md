<objective>
Build a lightweight, forward-only migration runner for HeySous's SQLite database using PRAGMA user_version as the version tracker. The runner uses a static registry of numbered migration functions, wraps each in a transaction, and integrates into createDatabase() between pragmas and table init functions.

Purpose: Future phases (26, 30) need safe, tracked schema changes. This framework replaces ad-hoc migration patterns with a ~50 LOC runner that is idempotent, transactional, and inspectable via `sqlite3 CLI`.
Output: `src/db/migrations.ts` with runner + empty registry, tests, and integration into `createDatabase()`.
</objective>

<task type="auto">
  <name>Task 1: Create migration runner with tests</name>
  <files>src/db/migrations.ts, tests/db/migrations.test.ts</files>
  <action>
Create `src/db/migrations.ts` with:

1. A `Migration` interface with `version: number`, `name: string`, `up: (sqlite: BetterSqlite3.Database) => void`.

2. An exported `migrations` array (typed `Migration[]`), initially empty. It is exported so tests can manipulate it, and so future phases add entries directly. Add a comment: `// Add new migrations here. Versions must be sequential integers starting at 1.`

3. A `runMigrations(sqlite: BetterSqlite3.Database): void` function that:
   - Reads current version via `sqlite.pragma("user_version", { simple: true }) as number`
   - Validates that all migration versions are sequential with no gaps (sort, check each is previous + 1 starting from 1). Throw an Error with a descriptive message if gaps are found. This is 3-4 lines.
   - Filters to `migrations.filter(m => m.version > currentVersion)` and sorts by version
   - Returns early if no pending migrations (no log output for this case)
   - Logs at info level: `"Running database migrations"` with `{ currentVersion, pendingCount }`
   - For each pending migration: logs `"Applying migration"` with `{ version, name }`, runs `sqlite.transaction(() => { migration.up(sqlite); sqlite.pragma(\`user_version = ${migration.version}\`); })()`, logs `"Migration applied"` with `{ version, name }`
   - After all: logs `"All migrations complete"` with `{ newVersion }`

4. Import `type BetterSqlite3` from `"better-sqlite3"` and `logger` from `"../logger.js"`. Follow ESM `.js` extension convention.

5. Export the `Migration` type for use by future phases.

Then create `tests/db/migrations.test.ts` with:

1. Import `Database` from `better-sqlite3`, import `runMigrations` and `migrations` from `../../src/db/migrations.js`.

2. Use an in-memory SQLite database (`new Database(":memory:")`) for each test. Set WAL mode and foreign keys pragmas to match production.

3. Tests:
   - "runs pending migrations and updates user_version": Push 2 test migrations to the `migrations` array (version 1 creates a table, version 2 adds a column). Call `runMigrations(db)`. Assert `db.pragma("user_version", { simple: true })` equals 2. Assert the table and column exist via `PRAGMA table_info`.

   - "skips already-applied migrations": Set `db.pragma("user_version = 2")`. Push 2 migrations (version 1 and 2). Call `runMigrations(db)`. Assert user_version is still 2 (no change). Assert the table does NOT exist (migration was not executed).

   - "is idempotent - second run is a no-op": Push 1 migration. Call `runMigrations(db)` twice. Assert user_version is 1. Assert no errors.

   - "rolls back failed migration and does not advance version": Push 2 migrations: version 1 succeeds (creates a table), version 2 throws an Error. Call `runMigrations(db)` and expect it to throw. Assert user_version is 1 (not 2). Assert the table from migration 1 exists. Assert the changes from migration 2 are rolled back.

   - "throws on non-sequential version numbers": Push migrations with versions [1, 3] (gap). Expect `runMigrations(db)` to throw with a message about non-sequential versions.

   - "handles empty migrations array": Call `runMigrations(db)` with no migrations pushed. Assert user_version is 0. No errors.

4. Use `beforeEach` to clear the `migrations` array (`migrations.length = 0`) and create a fresh in-memory database. Use `afterEach` to close the database.

5. Use `vi.mock("../logger.js")` to mock the logger so tests don't produce console output. Alternatively, if mocking is complex, just let it log -- the tests are fast enough.

IMPORTANT: Use `.js` extensions on all imports in the test file.
